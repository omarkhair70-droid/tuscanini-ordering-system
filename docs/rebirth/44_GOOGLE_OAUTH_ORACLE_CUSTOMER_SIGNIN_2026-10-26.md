# Google sign-in for Tuscanini (draft-only)

Google authenticates the browser. The Next.js callback exchanges an authorization code with Google using a server-side OAuth client secret and PKCE. It passes only the resulting Google ID token + nonce through the existing authenticated internal service API. Oracle independently checks the signed Google JWT against Google's rotating signing keys and validates issuer, audience, expiry, verified email, stable `sub` and nonce. An Oracle-only opaque, hashed-at-rest customer session is then issued as an HttpOnly cookie by Next.js.

No email OTP provider or Resend account is required for Google sign-in. The old email OTP route remains dormant and disabled by default. **Never match Google accounts to previous accounts by email/phone alone.** Unique Google subject is authoritative; attempts to claim an email already held by an unlinked OTP user fail closed rather than silently merge identities.

**Activation is NOT part of this code commit.** On the existing Coolify Dockerfile application, provision `GOOGLE_OAUTH_CLIENT_ID` and `CUSTOMER_GOOGLE_AUTH_ENABLED=yes` only after this migration and staging validation. On Vercel Preview configure `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REDIRECT_URI`, and `TUSCANINI_ORACLE_CUSTOMER_ACCOUNTS_READY=yes`. Use a separately registered, exact HTTPS redirect URI `https://YOUR-PREVIEW-HOST/api/customer/google/callback`, Google OAuth client of type **Web application**, scopes `openid email profile`. Production Google client/redirect should be configured separately. Keep `ORDER_API_ACCEPT_ORDERS=no` and `CUSTOMER_AUTH_ENABLED=no` while staging sign-in.

Migrations: add `schema-google.sql` after existing customer/account migrations. Coolify's existing Dockerfile app executes migrations on restart, so confirm backups and staging before redeploy. No need for a second PostgreSQL container or Compose app.

## Implementation and operational handoff
- The browser opens `/api/customer/google/start`, which creates random `state`, `nonce` and PKCE S256 verifier in a ten-minute HttpOnly, SameSite=Lax, host-only cookie. Next redirects to Google requesting only `openid email profile`.
- On `/api/customer/google/callback`, Next checks the exact state, exchanges the code with Google using its server-only client secret and PKCE verifier, and sends Google's ID token + expected nonce through the internal, service-key authenticated Oracle API.
- Oracle validates the JWT signature with Google's rotating JWKS, `iss`, `aud`, `azp` when present, timestamps, `nonce`, `email_verified`, and Google `sub`. Only that stable Google subject identifies the account. Contact email is not used to claim an unrelated account.
- Oracle creates its own random, hashed-at-rest 30-day customer session; Next sets the existing protected customer cookie. Existing guest ordering, addresses and order history consume the same session.
- Tests include signed Google JWT, token forgery, wrong audience, expired token, unverified email, nonce mismatch, same-subject repeat, and refusal to merge unrelated preexisting email accounts.

## Exact setup in existing environments (manual credentials; no prod flag changes)
1. In [Google Auth Platform](https://console.cloud.google.com/auth/clients), make a **Web application** OAuth client for the **actual fixed HTTPS Vercel preview domain**, separate from production. Add exact redirect URI `https://YOUR-PREVIEW-DOMAIN/api/customer/google/callback`; Google requires an exact match.
2. In **Vercel Preview** for the same branch, set server-only `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REDIRECT_URI` (exact Google-registered callback), and only when connected and tested `TUSCANINI_ORACLE_CUSTOMER_ACCOUNTS_READY=yes`. Existing `ORDER_BACKEND=oracle`, `ORDER_API_ORIGIN` and `ORDER_API_SERVICE_KEY` must remain correct. Do not use `NEXT_PUBLIC_` for secrets.
3. In **existing Coolify Dockerfile service `tuscanini-orders-api`** (not a new Compose deployment), set `GOOGLE_OAUTH_CLIENT_ID` equal to Vercel's OAuth client and `CUSTOMER_GOOGLE_AUTH_ENABLED=yes` only after the new database migration and staging verification. Keep `CUSTOMER_AUTH_ENABLED=no` and `ORDER_API_ACCEPT_ORDERS=no`; **no Resend key is needed**.
4. Redeploy the **existing service** only after backup and review of new additive `schema-google.sql`, then verify startup, `/readyz`, signed-in Google flow, email collision denial, logout, private history and save/delete address on two browsers. Do not turn on real order intake.
